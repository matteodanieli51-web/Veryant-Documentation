# Runtime Errors

Except for few runtime errors (e.g. "missing license" and "unsatisfied link error") runtime errors are identified by exception messages produced by the Java virtual machine. They can be printed on the console or returned as a graphical message box depending on the error type and on [iscobol.exception.message](../SDK-Users-Guide/Compiler-and-Runtime/Configuration/Configuration-Properties#exception_message) setting.

The exception message is usually followed by a stack that lists all programs and paragraphs that are involved, from the one that produced the error to the first one that were executed. Compile with -g option to see references to the COBOL source into the stack, otherwise you’ll see references to the intermediate java source that were generated by the isCOBOL Compiler to produce the final class object. When “unknown source” appears in place of the source reference, it means that the corresponding Java program didn’t include debug information (it usually happens with isCOBOL internal objects, since the isCOBOL Framework is compiled without debug information).

This article examines the most common runtime errors, providing suggestions about how to address them.

## Standard runtime errors

The errors listed below are produced by the runtime system. They can be reproduced running in stand-alone mode as well as running in thin client mode.

| Message | Meaning |
| --- | --- |
| Accept executed on an invisible window: <br><window-title\>  | This error is returned when the program tries to accept the user input on a window whose [Visible](../User-Interface/Controls-Reference/WINDOW/Properties/Visible) property is set to zero. |
| Accept in event procedure. <br>Event-Type: #### | This error is returned when an ACCEPT on the GUI is performed in the code of a non-terminating event. The Event-Type value tells which event has caused the error. In order to resolve this problem, the ACCEPT must be moved outside the handling of the event, after a terminate action has been performed in the event.<br>Example of problematic code:  <br><br>perform until crt-status = 27    <br>accept screen-1        <br>on exception           <br>continue     <br>end-accept <br>end-perform. <br>...<br>screen-1-grid-1-events. <br>evaluate event-type <br>when msg-goto-cell <br>when msg-goto-cell-mouse     <br>\|some operations     <br>accept screen-2<br>end-evaluate. ``` <br><br>Example of problem resolution:  <br><br>perform until crt-status = 27    <br>accept screen-1        <br>on exception          <br>continue    <br>end-accept    <br>if flag-terminate-accept = 1       <br>move 0 to flag-terminate-accept       <br>accept screen-2    <br>end-if <br>end-perform. <br>...screen-1-grid-1-events. <br>evaluate event-type <br>when msg-goto-cell <br>when msg-goto-cell-mouse      <br>\|some operations      <br>move 1 to flag-terminate-accept      <br>set event-action to event-action-terminate <br>end-evaluate. |
| Action in event procedure | This error is returned when the ACTION property of a Grid or Tree-View is modified within MSG events handling (e.g. *MODIFY screen1-gr-1 ACTION ACTION-ENTRY* within the handling of the MSG-GOTO-CELL event). <br>Such operation is not allowed by isCOBOL. |
| Active window is modal: <br>can't create a modeless child window | This error is returned when the program tries to create and activate a modeless window (e.g. an independent window) but the current window is modal (floating windows are modal by default) and the focus cannot be moved until the current window is closed. |
| Active window is modal: <br>cannot change the active window | This error is returned when the program tries to activate another window but the current window is modal (floating windows are modal by default) and the focus cannot be moved until the current window is closed. |
| CALL not found: <br><program_name\>  | This error is returned when a called subroutine cannot be found and the CALL statement doesn’t have a ON EXCEPTION\|OVERFLOW clause. <br>The same error is returned when a remote subroutine crashes and doesn’t return to the calling program. |
| CALL not found: <br>C function system() | This error is returned when you call either C$SYSTEM or SYSTEM routines having *iscobol.system.exec=c* in the configuration and the dyncall library (installed with isCOBOL) can’t be found in the Java library path. <br>Only on Windows, the error can be returned also if msvcrt.dll can’t be found in the Java library path. |
| com.iscobol.rts.IscobolRuntimeException: <br>Internal error: Missing CLSID | This error is returned when the program displays a JAVA-BEAN control without the CLSID property set. <br>Unlike most runtime errors, this error is always displayed on the console, regardless if a graphical environment is available or not. |
| com.iscobol.types.<type\> cannot be cast to <br>com.iscobol.types_n.<type\> <br>or <br>com.iscobol.types_n.<type\> cannot be cast to <br>com.iscobol.types.<type\> | These errors are returned when you try to exchange parameters between a program compiled with the [-cp](../SDK-Users-Guide/Compiler-and-Runtime/Compiler/Compiler-Options#cp) option and a program compiled without the [-cp](../SDK-Users-Guide/Compiler-and-Runtime/Compiler/Compiler-Options#cp) option. <br>If you choose to adopt the [-cp](../SDK-Users-Guide/Compiler-and-Runtime/Compiler/Compiler-Options#cp) option, you should compile all the programs with this option. |
| Could not load the main class | This error is usually returned by javaw.exe on Windows. It means that the class has been found but there were problems while running it, for example if the license is missing. <br>Use java.exe to see a more complex error message that will help in diagnosing the problem. |
| <error_description\> <logical_filename\> <br>(<physical_filename\>)FS=[<file_status\>],<br>EXFS=[<extended_status\>]: <error_description\>  | This kind of error is returned when an I/O error occurs while working with a file and the program doesn’t contain DECLARATIVES for the file and [iscobol.file.errors_ok](../SDK-Users-Guide/Compiler-and-Runtime/Configuration/Configuration-Properties#file_errors_ok) is set to false. |
| Internal error: <br>Concurrent access to <item_name\> group-item | This error is returned when two threads access the same group data item at the same time.<br>During a CALL THREAD, if you're not interested in checking the parameters after the CALL has started, consider passing these parameters either BY CONTENT or BY VALUE. If you need to pass the parameters BY REFERENCE, instead, use the [SYNCHRONIZED](../Language-Reference/Procedure-Division-Statements/SYNCHRONIZED) statement to avoid the concurrent access on these parameters.<br>During a PERFORM THREAD, having two threads using the same data item, you can define the item with the [IS THREAD-LOCAL clause](../Language-Reference/Data-Division/Data-Description/IS-THREAD-LOCAL-clause) (or add it to the [THREAD-LOCAL-STORAGE Section](../Language-Reference/Data-Division/Thread-Local-Storage-Section) of the program). <br>In this way each thread uses its own copy of the data-item and there's no concurrency. <br>Instead, if you need to have both threads working on the same data item, use the [SYNCHRONIZED](../Language-Reference/Procedure-Division-Statements/SYNCHRONIZED) statement to avoid the concurrent access on the data-item. |
| Internal error: <br>IIOP: Communication problem(s) <br>[java.io.IOException: Cannot run program <program-name\> | This error is returned when [iscobol.file.index](../SDK-Users-Guide/Compiler-and-Runtime/Configuration/Configuration-Properties#file_index) is set either to “dcic”, “fscsc”, “mfc” or "vfc" and the isCOBOL Framework cannot find the proper executable file. <br>Ensure that the executable is in the system Path or set *iscobol.file.connector.program*.* properties to indicate where it is. |
| Internal error: <br>java.lang.IllegalArgumentException: ct_init ERROR 19:133:0 | This error is returned when isCOBOL is not able to connect to the c-tree server. The two common causes are<br><br>• the c-tree server is down or unreachable, or<br>• the c-tree client library version doesn’t match with the c-tree server version |
| Invalid handle | This error is returned when the program performs a MODIFY or an INQUIRE on a graphical control that doesn’t exist yet or has been destroyed. <br>You can avoid this error by setting [iscobol.gui.ignore_invalid_handle](../SDK-Users-Guide/Compiler-and-Runtime/Configuration/Configuration-Properties#gui_ignore_invalid_handle) to 1 in the configuration; in this way MODIFY and INQUIRE statements on invalid handles will have no effect, but nobody will be advised about it. |
| Invalid isCOBOL rts version build #xxx or later required | This error is returned by Database Bridge subroutines when they’re not compatible with the current runtime version. |
| java.lang.ArrayIndexOutOfBoundsException | This error means that a Java array has been referenced out of its bounds. In COBOL programs it usually refers to an OCCURS data item that it referenced outside of its occurrences (i.e. consider having 77 data-item1 PIC X(10) OCCURS 10. and performing MOVE SPACES TO data-item1(11). ). |
| java.lang.NoClassDefFoundError <br>or <br>java.lang.ClassNotFoundException | These errors mean that a java class was not found by the JVM. <br>It can be returned at startup if the main program name has not been passed correctly in the command line (consider that Java is case-sensitive and the .class extension must be omitted) or if a typo caused Java to treat an option in the command line as if it was the program to launch. |
| java.lang.NullPointerException | This error is returned when the JVM tries to use an object that is not available. <br>In COBOL programs it usually refers to a data item. <br>A typical case in which this error appears is when a called program tries to use a linkage item that was not passed by the caller. |
| java.lang.OutOfMemoryError: <br>Java heap space | This error means that the JVM ran out of memory. <br>To avoid it, you must increase the memory limit by adding -Xmx256m Java option to the command line. <br>256 means 256 MB and it specifies the maximum amount of RAM that the JVM can allocate. <br>If it’s not enough, try with higher values. |
| java.lang.OutOfMemoryError: <br>Metaspace | This error means that the non-heap memory limit of the JVM has been reached. <br>The non-heap memory is used to store class descriptions, so this error may appear when running huge applications. <br>To avoid it, you must increase the non-heap memory limit by adding -XX:MaxMetaspaceSize=1g and -XX:CompressedClassSpaceSize=1g Java options to the command line. "1g" means 1 GB and it specifies the maximum amount of non-heap memory that the JVM can allocate. <br>Compressed Class Space contains internal representation of Java classes, while Metaspace holds all the rest metadata: methods, constant pools, annotations, etc. If these values are not enough, try with higher values. |
| java.lang.OutOfMemoryError: <br>unable to create new native thread | This type of OutOfMemoryError is generated when an application isn’t able to create new threads. <br>This error can occur if there is no room in the memory to accommodate new threads or if the number of threads exceeds the operating system limit. <br>In order to know what’s the maximum number of threads allowed by the host operating system, you can run the ISCHECK program installed with isCOBOL in the folder “sample/limit-tests”. |
| java.lang.reflect.InvocationTargetException | This error is returned when a problem occurs during the invocation of a Java object. In isCOBOL it’s usually caused by missing libraries. <br>Check the exception stack to retrieve more information on the cause. |
| java.lang.StackOverflowError | This error means that the thread stack area in the Java virtual machine was overloaded. <br>To avoid it, increase the thread stack size using the Xss Java option. The error may also depend by an error in the COBOL code, like a program that calls itself recursively a infinite number of times. |
| java.lang.UnsatisfiedLinkError: <br>no <library-name\> in java.library.path | This error means that the JVM failed to load a native library. <br>The library name is traced in the error message. A typical case in which this error can appear is when iscobol.file.index is set to work with c-tree (e.g. iscobol.file.index=ctreej) and isCOBOL is not able to find the c-tree client library (ctree.dll on Windows and libctree.so on Unix). <br>On Windows machines, native libraries are loaded from the paths listed in %PATH% environment variable. <br>On Unix, they’re loaded from the paths listed in $LD_LIBRARY_PATH environment variable (be aware that the name could be different depending on the o.s.). <br>To specify the library path in a cross-platform way, you can take advantage of the -Djava.library.path Java property (i.e. java -Djava.library.path=/home/isCOBOL2010/native/lib MAIN). |
| java.lang.UnsatisfiedLinkError: <br>Native Library <library-name\> already loaded in another classloader | This error is typical in servlet containers like Tomcat. <br>It occurs if two web applications try to load the same dynamic link library. <br>It can happen with COBOL applications using file handlers that have native dependences, like [DCI](../SDK-Users-Guide/Files-Management/Indexed-Files/DCI) for example. In order to avoid it, consider a file connector solution if available. <br>For example, with DCI you can use [The DCI File Connector](../SDK-Users-Guide/Files-Management/Indexed-Files/File-Connectors/DCI-File-Connector). |
| java.lang.UnsupportedClassVersionError: <br><program-name\> has been compiled by a more recent version <br>of the Java Runtime (class file version <n\>), <br>this version of the Java Runtime only recognizes class file versions up to <n\> | This error is returned when the JRE associated to the isCOBOL runtime is not able to execute the program class, as this class was produced by a more recent Java version. <br>To match the value of n with the corresponding Java version, refer to [Java major version numbers](./Version-numbers#java-major-version-numbers). |
| Missing license: <br>The license key is missing, invalid or has expired!<br>Check your properties files or contact Veryant or your distributor for technical support. | This error is returned at startup if the license is not found or is expired. <br>Contact your Veryant’s representative to obtain a valid license. <br>Consult the chapter [Getting Started](../SDK-Users-Guide/Compiler-and-Runtime/Getting-Started/getting-started) to know how to install the license correctly. |
| Native call not found | The error message "Native call not found" means that the COBOL program has called a C language (native) function that has the same name as the native library (.dll or .so), but the function does not exist. If you get the error "Native call not found" and you do not mean to call a native library (i.e. you are trying to call a COBOL program) then there may be a DLL or shared object library with the same name as the COBOL program in the library search path. |
| Nested Accept in embedded procedure. | This error can be generated only if the [iscobol.gui.nested_embedded_proc_check (boolean)*](../SDK-Users-Guide/Compiler-and-Runtime/Configuration/Configuration-Properties#gui_nested_embedded_proc_check) configuration property is set to true. <br>The error is raised when the code of an embedded procedures performs an ACCEPT on the GUI generating nested embedded procedures. |
| Unmatching DYNAMIC LENGTH items in LINKAGE SECTION | This error is returned when a called program receives a GROUP-DYNAMIC parameter (e.g. a group that includes dynamic length items like X ANY LENGTH or OCCURS DYNAMIC) that doesn’t match with the parameter definition in the Linkage Section. <br>The error message is followed by the name of the data item that caused the mismatch. |
| Unmatching DYNAMIC LENGTH items in LINKAGE SECTION: <br><source_item_name\> dyncount=<source_count\>; <br><dest_item_name\> dyncount=<dest_count\> | This error is returned when a GROUP-DYNAMIC data item (a group item that includes dynamic length items or dynamic capacity tables) is exchanged between two programs and the definition in the caller program doesn’t match with the definition in the called program. <br>In particular, the error is returned when the number of dynamic elements expected by the called program is greater than the number of dynamic elements passed by the caller program. |
| java.lang.IllegalAccessError: superclass access check failed: class <br>com.iscobol.gui.client.swing.IscobolWindowsComboBoxUI <br>(in unnamed module @0x5ef04b5) <br>cannot access class <br>com.sun.java.swing.plaf.windows.WindowsComboBoxUI <br>(in module java.desktop) <br>because module java.desktop does not export <br>com.sun.java.swing.plaf.windows to <br>unnamed module @0x5ef04b5 | This error occurs when displaying a Combo-Box control using the the WindowsLookAndFeel with Java version 17 or higher. <br>To avoid the error, the following option must be added to the command line: <br>*--add-opens java.desktop/com.sun.java.swing.plaf.windows=ALL-UNNAMED*.<br>Windows wrappers like isrun.exe and isclient.exe take care of using this option when the Java version is 17 or higher, so no action is required.<br>The option must be added to the command line when using java commands, e.g.<br>**java --add-opens java.desktop/com.sun.java.swing.plaf.windows=ALL-UNNAMED com.iscobol.invoke.Isrun ..**. <br><br>**java --add-opens java.desktop/com.sun.java.swing.plaf.windows=ALL-UNNAMED com.iscobol.gui.client.Client ...** |
| This object incompatible with this runtime version: <br>rts=<*version_string*\>,obj=<*build_number*\> | An isCOBOL Runtime can run objects compiled by a Compiler of the same version or of a previous version. If this error occurs, you’re trying to run an object compiled by a newer version of the Compiler. Refer to isCOBOL builds for the list of build numbers and versions. |

## Application Server (Thin Client) errors

The errors listed below can occur only in a thin client environment.

| Message | Meaning |
| --- | --- |
| com.iscobol.rmi.RemoteInvocationHandler$1: <br>Call timed out. Current timeout=0 | This error is returned when the program invokes a method of a Java-Bean passing an object reference among parameters and the client JVM is not compatible with the server JVM for the transmission of the object reference. <br>In order to ensure that the cause of this error is actually the invocation of a Java-Bean method, check the exception stack and look for occurrences of “com.iscobol.gui.server.CobolGUIJavaBean.callMethod”. <br>Use the same JVM version on both client and server side to get rid of this error. |
| com.iscobol.rts.IscobolRuntimeException: <br>License exceeded <count\> | This error is returned when a client connects to the Application Server but there are no more slots available because they have been used by other clients. <br>You must wait for another client to disconnect before being able to connect to the Application Server, or you can upgrade the license in order to have more concurrent connections to the Application Server. <br>See [Users count](../../is-cobol-AS/Usage-of-isCOBOL-Server/Users-count) for information about concurrent client connections to the Application Server. |
| Disconnected from <ip\>, port <port\> | This error is returned when the connection to the server terminates unexpectedly, e.g. if a severe exception occurs server side. <br>If you don't want to be notified, you can add the *-nodisconnecterr* option to the isCOBOL Client command line. |
| ERROR: <br>Client release <n1\> is incompatible <br>with Application Server <n2\> | This error is returned when the isCOBOL Client connects to an Application Server in thin client environment, but the versions of the two products are not compatible. <br>Update the isCOBOL installation in order to make these versions match. |
| iscobol.as.stop_thread not supported with Java > 19 | Java removed the deprecated Thread.stop method in version 20, therefore the isCOBOL Server can’t provide the "stop thread" feature anymore under Java 20 or greater. <br>Remove the [iscobol.as.stop_thread *](../SDK-Users-Guide/Compiler-and-Runtime/Configuration/Configuration-Properties#as_stop_thread) setting from your configuration or downgrade the Java version to avoid this error. |
| java.net.BindException: <br>Address already in use | This error is returned starting the ApplicationServer if the port on which it must listen for connections is already used by another process. |
| Max number of connections reached: <br><count\> | This error is returned when the isCOBOL Client connects to an Application Server in thin client environment but there are no more connection slots available. <br>The number at the end of the message is the current connection limit. <br>See [Connections count](../../is-cobol-AS/Usage-of-isCOBOL-Server/Connections-count) for information about user count in Application Server environment. |
| Session terminated by the Server | This error is returned when the connection to the server is terminated by the administrator. |
| Software Incompatibility<br>Client release (<*cs_version*\>) is incompatible <br>with Application Server (<*cs_version*\>) | The C/S version of isCOBOL Client must match the C/S version of the isCOBOL Server otherwise this error is returned. <br>The C/S version changes at each release, so probably your Client and Server are from different releaes. <br>You can double check the C/S version of the products through the commands *iscclient -v* (on the client) and *iscserver -v* (on the server). <br>Refer to [isCOBOL C/S version numbers](./Version-numbers#iscobol-cs-version-numbers) for the list of C/S version numbers and their corresponding isCOBOL release. |
| Unable to connect to <ip\>, port <port\> | This error is returned when the server can’t be reached by the client. The most common causes are:<br><br>• wrong IP or port specified<br>• different hostname values used on client and server command-lines. E.g. the server was started with *-hostname 127.0.0.1* (server’s localhost address) and the client is launched with *-hostname 192.168.1.1* (server’s IP address)<br>• the server is down<br>•the server port is blocked by a firewall |
